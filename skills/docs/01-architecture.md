# 01 · 总体架构

## 三层分工

```
┌──────────────────────────────────────────────┐
│ 宿主 agent（用户的 AI，自带工作区/工具调用/看图） │  元决策层
│  读状态 → 决定粒度 → claim 任务 → 干活 → submit │
├──────────────────────────────────────────────┤
│ 薄机器接口（CLI 优先，MCP 为壳，同一套函数）      │  传输层
│  status / claim(n) / submit(batch) / note /    │
│  profile_update / issue_add / pause / resume   │
├──────────────────────────────────────────────┤
│ skills 内核（Go，确定性，零 LLM API）            │  执行+校验层
│  阶段状态机 / 任务队列(租约) / 验收器 /           │
│  本地算法(dedupe/索引/覆盖率/编译门禁) /         │
│  项目注册表 / 书级 profile                      │
└──────────────────────────────────────────────┘
```

分工红线：

- **agent 只做元决策**：定粒度（整步 / 单章 / 重试 / 切回）、看图验收、授权级决策。永不亲自编排阶段流，永不自记状态。
- **kernel 只做确定性的事**：一切"对/错"由代码判，一切"怎么做好"让 agent 判。
- agent 用它的原生工具（看图/read_file/写草稿）直接操作磁盘；kernel 只在 submit 时验收。**不要约束 agent 的读写，验收口才是边界。**

## 状态三层分离（核心不变量）

| 层 | 内容 | 写者 | 读者 | 上下文丢失后果 |
| --- | --- | --- | --- | --- |
| 制品层（唯一事实源） | 分类结论、tikz、章节 .tex、编译产物、sha256 | kernel 验收后落盘 | 双方 | 无损，从磁盘重建 |
| 任务层 | 队列：id、输入路径、验收条件、状态、租约 | kernel | agent | 无损，队列即进度 |
| 笔记层（一次性记忆） | scratch 草稿 + notes.md 蒸馏结论 | agent | agent 自己 | 只损失舒适度 |

**agent 上下文里不保存任何进度。** 看图遵循"打开 → 决策 → 写进笔记 → 从脑子里清掉"，图是上下文里最贵的东西，串味只影响逐图隔离的笔记文件，不影响正确性。

进度永远从制品层确定性重建：`progress.json` 只是缓存；同样的磁盘状态必然产生同样的任务派发序列（可调试、可复现）。

## 自动驾驶主循环

```
INIT → PREP(split/mineru/organize，纯 kernel 自动) → QUEUE
  → DISPATCH(agent claim) → VERIFY(kernel 验收) → QUEUE
  → …各阶段推进… → ASSEMBLE → FINAL CHECK → DELIVER
```

- 无 LLM 阶段（前置流水线、索引构建、本地 dedupe 扫描）kernel 一口气跑完，不需要 agent 在场——"放下 PDF 就能走开"的底气。
- 租约带过期时间：关电脑 = 租约过期、任务回队列；下次冷启动仪式无损续上。
- 用户命令只有三个：`暂停`（任务边界停派，原子性保证不半截）、`看进度`、`终止`（归档现场，等价旧版 clean 脚本的备份语义）。
- 默认零交互：能代码判的不问人；人工确认降级为可选高级开关。
- 批间护栏：每阶段第一批 3–5 个任务冒烟试跑 + 验收，通过才放量。

## 项目注册表与书级档案

```
registry.json：每本书 = 生命周期(active/paused/archived) + 当前阶段 + 队列深度 + 最后活跃时间
切换书 = 改 active 指针（原书 paused，任务边界自然停）
封存 = 队列冻结只读，清可再生中间产物，保留制品、分类结论、样式包与 profile.md
```

每本书工作区内 `profile.md`（append-only，经 `profile_update` 写入）积累本书特有知识：OCR 系统性毛病、样式陷阱、跑出来的特例规则（如"某类裁图不得与某类标识合并"）、已验收的好案例。派发任务时 kernel 把 `profile.md` 与全局说明书一起塞进任务包——**书越跑越聪明，经验存在书里，不存在任何上下文里**。

## 记忆泡泡（任务沙箱）

```
tasks/<task_id>/
├── inputs/      kernel 铺好的输入（只读：图、源文本、说明书、书档案、白名单路径）
├── scratch/     agent 草稿区：随便建/改/写尝试/存失败稿（泡泡本体）
├── notes.md     蒸馏笔记（append-only）：结论、坑、交接语
├── out/         待提交产物（submit 从这里收）
└── verdict.json # kernel 写的验收结果
```

- 切换任务 = 换指针不搬数据；旧 scratch 原地留在磁盘（放到架子上，不是捏碎）。
- 重入 O(1)：rework 回到任务 A 时 scratch 原样在；配一条廉价仪式——交还任务前在 notes.md 追加两行交接语（"停在 X，下一步 Y"），重入先读这两行。
- 纪律：notes.md 记结论，scratch 记过程；上下文里永远只带 scratch 的文件名索引，不带内容。

## 共享区

只读共享（style/、已转换章节、各章报告、doc_index、figures 池、dedupe 代表图）：任务包里列白名单路径，不设物理只读；submit 验收时凡引用越界/被篡改路径的直接打回。

可写共享仅三样，必须 kernel 中介（append-only 语义，禁止裸写文件）：

| 共享物 | 工具 | 原因 |
| --- | --- | --- |
| 本书 profile.md | `profile_update(append)` | 将来开子智能体时不互相覆盖 |
| issues 存储 | `issue_add / issue_resolve` | kernel 据此派 rework 任务，必须结构化 |
| 全局状态摘要 | kernel 自写 | status 产出物，agent 只读 |

## 编排记忆：队列依赖边

旧架构的"会话树编排"（request_chapter_split → 子会话排队 → 父等子）在新形态下是**队列里的父子指针**：

转换任务发现章节过大 → agent 提交拆分提案（2–16 段、行号区间）→ kernel 验证（完整、连续、无重叠）→ 子任务入队、父任务 `blocked` → 子任务全部 pass 后父任务解锁。DFS 递归细分 = 父子指针链，最多三层（沿用旧线判据）。回炉同理：核对发现问题 → `issue_add` → kernel 生成 rework 任务 → 原任务 blocked 于 rework。

旧版"等待并发槽/父等子"的进程内编排代码全部消失。

## 四层记忆总览

私有泡泡（scratch+notes）管局部记忆；共享区管协作记忆；队列依赖边管编排记忆；书级 profile 管长期记忆。四层全在磁盘上，agent 上下文只是它们的瞬时投影。

## 并发预期

- kernel 内并行不变：MinerU、编译、本地扫描照旧并行。
- LLM 阶段吞吐 = 1×agent（平台给子智能体则乘子智能体数，属平台能力，不为它在内核造轮子）。
- 缓解：延迟批量核对、dedupe 代表图（画一张跟随一批）、同类任务连发、批量 claim/submit。

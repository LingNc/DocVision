## P40 整组核验必须能续跑（用户提问触发，T121）

## P42 输出预算必须给输入让路（同一轮运行的真实事故触发，T123）

  - 事故：某项目整组核验（336 张）。窗口 262144、`max_tokens=131072`，会话跑了 18 分钟把 prompt 推过 131072（最后一条 `[context] 估算 132107 tokens，窗口的 50%`，离压缩线 85% 很远），22:28:00 那一轮就 `HTTP 400`（流式失败→非流式重试同样 400；厂商按 prompt+max_tokens 卡窗口），整桶核验作废、`[dedupe] 核验会话失败，该批图片保持独立`，288 张图白看——这不是限流也不是余额，是纯粹的算术没算。
  - 约定：`max_tokens` 是**上限**不是承诺；每次请求前按「窗口 − 当前上下文 − 余量」算预算，装得下不动、装不下退让。上下文规模沿用压缩那套口径（本地估算 / 标定估算 / 厂商实测 `prompt_tokens` 取最大），余量取 2%（至少 1024），下限 512。
  - 压缩与输出预算分工明确：压缩管「输入别涨太大」，预算管「输入涨了也别把输出算漏」；不许用"调小 max_tokens 配置"当解法——那是让所有会话永久少输出。


## P43 同一份文件只核验一次、只画一次（T124）

  - 事实：某项目 388 条图片引用只有 130 份不同内容；336 张的核验桶里 296 张是逐字节副本（90 份内容），16 张的会话是 4 份。图片文件名里那串 64 位十六进制**不是**内容哈希（MinerU 按图片引用各发一个名字），内容身份只能自己算。
  - 用户口径：这些副本确实是同一张图（"确实都一样"），不应该让模型一张张重复看；最终从「两条都做」里定的是——看一份等于全部看过，并且会话里只留一份。
  - 约定：**逐字节一致 = 同一张图片**，这是身份判定而不是相似度推断，所以①候选池按 `sourceHash`（文件字节 `sha256`）收缩后才进会话/相似度检测；②副本不进会话、不占 id，核验结束后跟随代表图的结论（代表图被合并 → 同一 leader；代表图独立 → 跟随代表图本身）；③`dedupe_checked` 可以随代表图一起置真，因为被看过的正是同一份字节。
  - 边界：只收缩**字节相同**的，不碰相似度判断；`MotifSimilarTo` 闸门、逐张未裁剪证据、组类别取多数、代表图无成品即解除跟随全部保持不变。相似度桶照旧在收缩后的池上计算（同一份内容的特征也相同，桶与成员不受影响）。
  - 代价：转录身份是成员集哈希，成员变少就换了文件名，旧会话（当时 336 张全死的那份）不再续跑；对用户是收益——它本来就终止在 400 上。

## P44 相似度检测要不要上 GPU（用户提出排期，2026-10-17）

  - 用户看到的描述是「O(N²) 里每对都重建两份像素特征，388 张约 7.5 万对」，因此问能不能用 GPU 并行加速。前半句现在不成立了：T122（P41）把特征改成每图只算一次，388 张 20.49s → 0.31s；T124（P43）再把候选池按文件字节收缩，该书这次实测 **130 份内容：解码 50ms + 检测 213ms**（C(130,2)=8385 对）。
  - 结论：**不上 GPU**。按重要性排——① 0.2 秒不在任何关键路径上（同一阶段的模型会话以分钟计，用户等待的是核验会话而不是扫描）；② 工作量本身很小（≤70px 缩略图上的整数比较），一次 CUDA 初始化加 H2D 拷贝就超过全程耗时；③ 会给一个零依赖的 Go 单文件二进制硬塞 CUDA/驱动依赖，换不到收益；④ 真正的复杂度在**对数**不在单对成本，GPU 不改变 O(N²)。
  - 将来真的慢了（一本书出现上千份不同内容）时的顺序：先用廉价预筛砍对数（指纹分桶 / 尺寸与墨迹密度过滤 / 早退比较），再把两两比较按 goroutine 分片到多核——都在 CPU 侧、不动判定阈值。GPU 只作为最后手段。
  - 触发条件（写死，免得反复讨论）：检测耗时超过约 2s（当前 0.2s）或不同内容数超过 2000 才重新评估；否则不碰。

## P45 motif_groups 要能「组内增删」和「只换代表图」（用户观察触发，T125）

  - 用户观察：「这个 motifgroup 的工具功能好像少了一点，比如从某个组中去除某个或者某些，或者向某组中添加某个或者某些？你看他们调用的，好像一直是清空再重写？」——原 op 集只有 list/add/update/delete/clear，`update` 是整组替换，确实没有组内增删。
  - 原则（定下来，后续清单类工具照此办）：**会话工具的写操作应该能只改"要改的那一点"**。让模型为了改一个字段重发整份数据，代价是双份的——token 线性增长，以及"重发时抄漏成员"这种静默错误（工具没法区分"故意删掉"和"抄漏"）。`problems`/`split`/`blocks` 这些结构化清单工具已有 `update` 单条语义，`motif_groups` 是唯一还要求全量重写的。
  - 语义约定：① `append {n,ids}` 幂等（已在组内算无变化）、跨组占用即整批拒（一个 ID 只能属于一个组，回执指出被哪个组占着）；② `remove {n,ids}` 严格（任一 ID 不在该组就整批拒，不做"能删多少删多少"的模糊成功）；③ 移走 key **不猜**新代表，清空并在回执里点名用 `update {n,key}` 指定；④ 不足 2 张自动解散该组——`groups.json` 的既有不变量是"组至少 2 个成员"，1 张的组等价于独立，留着只会让 `submit` 报无意义的缺 key。
  - 边界不变：整批原子（失败一个字不写）、每次校验后立即落盘、`groups.json` schema 不变、`submit` 的缺 key / 未看过门禁不变、提示词只删了那行过期的 op 枚举。

## P46 核验会话要能并排比较，且后果不能沉默（T126）

  - 用户看到的现场：「他都看了好多了然后最后还看了一下 list 为空还提交了？」——90 张全看过、`submit {}` 0 组，整本书的图逐张重画。
  - 三个方案，用户逐条定了口径：**A 把后果写进回执/小结（做）**、**B 改提示词里 `crop` 那句（不做）**、**C 并排比较图（做）**。B 被否的理由是用户的原话「可见差异的话这个很难说，因为有的裁剪确实不能合并，有的无效裁剪确实可以合并」——`crop` 到底算不算差异只能看图判断，写成规则就会在两次运行之间给出互相矛盾的指令。所以**提示词里那条规则一个字不动**，只给它补一条比较手段与一句"这不是证据"。
  - `compare_images` 的边界（定下来）：输入只收模型自己点名的 2–4 个 id（超过 4 张就是联系图，T118 已经证明那种东西会被拿来替代逐张检查）；输出一张合成图 + 每张的像素尺寸与长宽比（裁切/比例差异用数字表达，不靠"看起来像"）；**不写 `seen`、不参与 submit 门禁**——比较图是判断辅助，证据永远是逐张未裁剪原图；格内等比缩放（CatmullRom，不 nearest，避免小图放大后笔画块状化被误读为"笔画不同"），每格标 id 并用灰框标出真实图幅（比例差异一眼可见）。
  - 沉默的后果要写进回执（而不是往提示词里加规则）：0 组提交必须写清"本次一张都不合并、N 张全部独立处理、预填的桶已被清空且不会自动恢复"；`clear` 必须写清删掉几组几张并点名 `remove`/`update`；核验结束必须有小结行，说明开过几个会话、合并几组、几张独立——会话进度行的 `N/M` 只是步数，不能当结论。
  - 不做的事：不改 `submit` 的接受条件（0 组仍是合法决定，代码没有资格替模型决定"必须合并"）；不改相似度闸门与逐张门禁；不给 `compare_images` 加批处理/整桶预览。

## P47 桶核验会话要有并发上限（T127）

  - 用户口径：桶之间本来互不依赖，"如果好多桶就照之前的规则并行"——但要能配置、默认值要保守（2），并且 `0` 要能退回串行。
  - 设计约束（定下来）：① 并发只发生在桶会话之间，**整理会话是屏障**（它消费所有桶交回的关键图，必须等全部结束）；② **完成顺序不能泄漏进结果**——结果按 scope 顺序收回，`applied` 的顺序因此与并发度无关，同样输入仍产生同样会话（否则日志、复跑、合并结论都会随调度抖动）；③ 失败计数与进度行必须是并发安全的（原子量），单个会话失败只丢自己那一格；④ 配置语义照 `models.*.extends` 的既有教训——`0` 是有效取值，所以"没写"只能在 YAML 节点层判定，默认值不能塞进 `setDefaults`。
  - 不做的事：不并发整理会话、不并发 process 阶段、不给 dedupe 加"整个阶段一起 429 重试"的新机制（沿用会话自身的重试与限流分流）。
  - 已知代价：每个会话都带自己的图片历史，并发 N 会把峰值内存与图片请求数放大 N 倍，所以默认 2、文档写明调高的代价。

## P48 对话页要看得见「会话为什么停」（T128）

  - 用户口径：报错终止的会话在网页上"看不到"，只有在 jsonl 里能查到——所以终点提示必须出现在默认页（对话），而不是藏在轨迹末行或详情栏里。
  - 设计约束（定下来）：① 只加**一条**尾巴，位置在消息流末尾、流式尾（PartialTail）之后；② 只在 `runEndError` 非空且会话不在运行时出现——正常结束不占位（否则每个会话都多一块噪音），运行中也不占位（错误是上一轮的旧账）；③ 文案分两行：固定标签「会话结局 · 错误终止」+ 原始原因，原因用等宽字体、`pre-wrap`、`break-word`（400/429 的原始报文不能丢信息）；④ 不改 `streamModel()` 的「meta 行不进消息流」这条既有设计——meta 归详情栏/轨迹，结局条是独立的一段，不是把 meta 塞回消息流。
  - 不做的事：不在侧栏每行写错误文本（徽标/琥珀点已经表达状态）；不把 `run_end` 也画成一条普通消息；不改 Go 侧数据（`RunEndError`/`endState` 早已下发，T99 完成）。
- 已知代价：无——这是纯前端呈现缺口，数据一直存在。
